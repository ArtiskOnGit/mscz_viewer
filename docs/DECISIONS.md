## Décisions

### ADR-001 — Lecture des `.mscz` : webmscore, à l'import uniquement — *Acceptée* (S1 validé le 2026-11-25, voir [résultats de la phase 0](spikes/PHASE0_RESULTATS.md))
- **Contexte** : aucune bibliothèque de rendu ne lit le format MuseScore, qui n'est pas documenté et change d'une version à l'autre. Il faut prendre en charge les fichiers **MuseScore 3.0 à 4.x et plus**.
- **Décision** : utiliser **webmscore** (MuseScore 4.0 compilé en WASM) pour convertir les fichiers en MusicXML et extraire les métadonnées et la timeline. MuseScore 4.0 sait ouvrir les fichiers 3.x, ce qui couvre normalement la plage 3.0–3.6.
- **Résultat de S1** : les fichiers **2.1, 3.6.2, 4.5.2 et 4.6.2** du corpus se chargent. `savePositions(true)` plante et corrompt l'instance WASM. Règle : **un worker neuf par import**, positions des mesures seulement. Import vérifié sur un vrai téléphone Android ; temps à mesurer.
- **Depuis** : webmscore sert aussi à importer le MusicXML (ADR-017) ; les parties masquées sont rendues visibles avant conversion (ADR-018).
- **Plans B** : a) recompiler webmscore sur un MuseScore récent ; b) convertisseur `.mscx` → MusicXML maison ; c) demander un export MusicXML (toujours pris en charge).

### ADR-002 — Rendu : Verovio sur MusicXML, mise en page adaptée à l'écran — *Acceptée* (S2 et S4 validés le 2026-11-25)
- **Décision** : **Verovio** (LGPL-3.0), toujours avec une **mise en page recalculée pour l'écran** (`breaks: 'auto'`). Les sauts de page et de système d'origine ne sont pas reproduits.
- **Non retenu** : le mode « mise en page d'origine » (SVG de webmscore). Il reste seulement un plan B technique si la qualité de Verovio est insuffisante.

### ADR-003 — Licence de l'application : GPL-3.0-or-later — *Acceptée*
- Imposée par webmscore. Verovio (LGPL), les polices (OFL) et les dépendances MIT/BSD sont compatibles.
- Le dépôt `ArtiskOnGit/mscz_viewer` a été privé pendant le développement, puis **rendu public le 2026-11-25** (obligation GPL : sources disponibles). Le lien « Source code » de l'écran À propos pointe vers ce dépôt.

### ADR-004 — Framework : Capacitor + Ionic **React** + TypeScript — *Acceptée*
- **Critère du porteur** : le plus simple et le plus multiplateforme.
- **Pourquoi React plutôt que Svelte** : Ionic ne propose officiellement que Angular, React et Vue, donc pas Svelte. React a le plus de documentation, d'exemples et de bibliothèques. Capacitor fournit Android, iOS et le web à partir de la même base.

### ADR-005 — Distribution : application Android + application web installable (iPhone) ; pas d'App Store — *Acceptée (2026-11-26, modifiée le 2026-11-27)*
- **Android** : APK direct (GitHub Releases), puis **F-Droid** et **Google Play**. La GPL ne pose pas de problème sur ces canaux.
- **Décision du porteur (2026-11-26) : pas d'application iOS native.** Le 2026-11-27, le porteur veut **aussi pouvoir utiliser Pupitre sur iPhone** : c'est fait **sans App Store**, par une **application web installable (PWA)** publiée sur GitHub Pages et ajoutée à l'écran d'accueil depuis Safari (**ADR-027**). Elle marche aussi dans tout navigateur récent (ordinateur, tablette, Android sans APK). L'application Android reste la version principale (« Ouvrir avec », « Partager vers », verrouillage de l'orientation).
- **iOS / App Store (pour mémoire)** : la compatibilité de la GPL avec les conditions de l'App Store est contestée. Une plainte d'un ayant droit de MuseScore pourrait faire retirer l'application. La PWA évite la question (pas de magasin, code source publié avec l'application). Si une application iOS native revenait un jour :
  1. publier quand même (risque accepté ; d'autres applications GPL y sont publiées) ;
  2. demander une autorisation écrite ou une exception à Muse Group (détenteur principal des droits) ;
  3. publier sur iOS une variante **sans webmscore** (import MusicXML seulement, voire un convertisseur `.mscx` maison sous licence permissive).
- Exigence commune : le pipeline d'import reste isolé derrière une interface (`ScoreImporter`) pour pouvoir remplacer webmscore sans toucher au reste.

### ADR-008 — Timeline du défilement et du métronome — *Acceptée* (S3 validé le 2026-11-25)
- Positions MuseScore (webmscore) à l'import pour les `.mscz`, avec reprises dépliées et changements de tempo. Timemap Verovio pour le MusicXML.
- La timeline contient aussi la **métrique de chaque mesure** (nombre de temps, unité), dont le métronome a besoin.
- **Résultat de S3** : l'ordre de jeu est identique entre MuseScore et Verovio (en retirant les suffixes `-rendN` de Verovio). Le filtrage des parties doit **recopier les tempos et repères** de la première partie (ADR-012).

### ADR-009 — Internationalisation : anglais d'abord, i18n dès le départ — *Acceptée*
- Langue de référence de l'interface : **anglais**. Le français est la première traduction ajoutée (phase 3) ; réglage « Langue » (langue de l'appareil par défaut).
- **i18next + react-i18next**. **Aucune chaîne en dur** dans les composants, ce qui est vérifié par une règle de lint (`eslint-plugin-i18next`).
- Clés structurées par écran (`library.import.button`), pluriels ICU, formats de date et de nombre via `Intl`.
- Noms de notes et de tonalités localisables : *C/D/E* en anglais, *Do/Ré/Mi* en français, et un réglage « notation des notes » indépendant de la langue (fait en phase 3 ; allemande *C D E … H*, B = Si♭).
- Interface prête pour les langues de droite à gauche (CSS logique : `margin-inline-start`…), sans en faire une priorité.
- La documentation du projet reste en français pour l'instant.

### ADR-010 — Pas de lecture audio ; métronome optionnel — *Remplacée par ADR-026 (2026-11-26)* pour la lecture audio ; le métronome reste tel quel
- ~~**Pas de synthèse audio** de la partition : pas de SoundFont, et pas de `synthAudio` de webmscore.~~ Le porteur du projet a changé d'avis : la partition peut être jouée (ADR-026).

### ADR-012 — Filtrage des parties : recopie des indications « système » — *Acceptée*
- **Contexte** (S3) : MuseScore n'exporte tempo, métronome et repères que dans la **première partie** du MusicXML. Si on la retire, tempos et timeline sont perdus.
- **Décision** : le module de filtrage recopie ces indications (`<sound tempo|dacapo|segno|dalsegno|coda|tocoda|fine>`, `<metronome>`, `<rehearsal>`, `<segno>`, `<coda>`) vers la première partie conservée, à la même position rythmique. Le prototype est dans `spikes/shared/filter-parts.mjs`.
- **Limite connue** : les textes système sans effet sonore (« Swing », titres de section) ne se distinguent pas des textes de portée en MusicXML. Ils ne sont pas recopiés pour l'instant.

### ADR-013 — Moteurs embarqués : tailles réelles — *Information*
- webmscore ~18 Mo (wasm 9,2 + mem 4,2 + data 4,1 + JS), Verovio ~8,4 Mo (WASM intégré au JS). Total des moteurs : **~27 Mo** dans l'APK.

### ADR-014 — React Router 6 malgré des alertes `npm audit` — *Acceptée (à revoir)*
- Ionic React 9 n'accepte que React Router `>=6.4 <7`. `npm audit` signale 3 vulnérabilités « modérées » corrigées en v7. Elles concernent les fonctions serveur et chargement de données, que nous n'utilisons pas : l'application n'a pas de serveur et ses routes sont locales.
- On repassera en v7 dès qu'Ionic le prendra en charge.

### ADR-015 — APK compilé par GitHub Actions, pas de SDK Android en local — *Acceptée*
- **Contexte** : le poste de développement n'a pas de SDK Android ; l'installer (Android Studio, ~10 Go) seulement pour produire un APK de test est lourd.
- **Décision** : la CI (`.github/workflows/ci.yml`, dépôt `ArtiskOnGit/mscz_viewer`) fait lint, typecheck, tests et build web, puis `cap sync android` et `gradlew assembleDebug` (JDK 21) sur un runner Ubuntu. L'APK est un artefact téléchargeable (`pupitre-debug-apk`, `gh run download`). Le développement courant se fait dans le navigateur et avec les scripts e2e (Chromium headless, émulation Pixel 7).
- **Conséquence** : chaque essai sur téléphone passe par un push sur `main`. Compiler en local reste possible (`npm run android`).

### ADR-016 — APK de debug signés avec une clé fixe stockée dans les secrets — *Acceptée*
- **Contexte** : chaque runner génère sa propre clé de debug ; Android refuse alors d'installer la nouvelle version par-dessus l'ancienne (il faut désinstaller, donc perdre la bibliothèque).
- **Décision** : un `debug.keystore` fixe, encodé en base64 dans le secret `ANDROID_DEBUG_KEYSTORE_B64`, est restauré dans `~/.android/` avant la compilation. Ce n'est **pas** une clé de publication : la release (phase 3) aura sa propre clé.
- **Si le secret est perdu** : en générer un nouveau ; une seule désinstallation sera nécessaire.

- **Correctif (2026-11-27, v0.7.1)** : jusqu'à la v0.7.0, la clé restaurée dans `~/.android/debug.keystore` n'était **pas utilisée** par le plugin Android Gradle sur le runner : chaque APK avait un certificat différent (vérifié sur les APK v0.6.1 et v0.7.0), d'où l'obligation de désinstaller pour mettre à jour. Désormais `app/build.gradle` déclare explicitement la clé (`signingConfigs.pupitre`, fichier `$PUPITRE_KEYSTORE`, PKCS12) ; les workflows décodent le secret dans `$RUNNER_TEMP`, la release échoue si le secret manque, et l'empreinte SHA-256 du certificat est affichée dans le journal (`439dc7dd…`). Une **dernière désinstallation** est nécessaire en passant à la v0.7.1.

### ADR-017 — webmscore pour tous les imports, MusicXML compris — *Acceptée* (écart avec la spécification initiale)
- **Spécification initiale** : analyser le MusicXML directement et calculer sa timeline avec la timemap de Verovio à la première ouverture.
- **Décision** : les `.mxl` / `.musicxml` passent aussi par webmscore (`WebMscore.load('mxl' | 'musicxml', …)`). On obtient le même MusicXML normalisé, les mêmes métadonnées et la même timeline (positions MuseScore, reprises dépliées) pour tous les formats : un seul chemin de code, testé.
- **Conséquence** : la timemap de Verovio n'est pas utilisée. Une variante iOS sans webmscore (ADR-005, option 3) devra la réintroduire.

### ADR-018 — Parties masquées rendues visibles à l'import ; version du pipeline et réimport automatique — *Acceptée*
- **Constat** (sur téléphone, fichier MuseScore 4.5) : les parties masquées dans MuseScore n'ont **pas de ligatures** dans le MusicXML exporté, car MuseScore ne les met pas en page.
- **Décision** : avant la conversion, une copie du fichier est modifiée pour rendre visibles toutes les parties et portées (`<Part><show>`, `<Staff><isStaffVisible>` en MuseScore 4, `<Staff><invisible>` en MuseScore 3). La visibilité d'origine est conservée pour choisir les parties affichées par défaut.
- Chaque partition mémorise `importerVersion`. Quand le pipeline change (`IMPORTER_VERSION`, actuellement 2), la bibliothèque **réimporte automatiquement** les partitions plus anciennes à partir du fichier d'origine conservé, en gardant identifiant, titre et réglages.

### ADR-019 — Mode Continu : pages Verovio empilées, rendu paresseux — *Acceptée*
- **Options étudiées** : une seule page très haute (une seule `renderToSVG`, mais un SVG énorme et un rendu long pour les gros conducteurs) ; pages de la largeur de l'écran avec `adjustPageHeight` empilées dans un défilement natif.
- **Décision** : la seconde. Le même worker Verovio produit des pages de la largeur de l'écran dont la hauteur suit le contenu. Seules les pages proches de la position de lecture sont dans le DOM (fenêtre de 4 pages rendues, 8 gardées) ; les autres sont des emplacements de hauteur mesurée ou estimée. La vue gère elle-même l'ancrage du défilement (`overflow-anchor: none`) pour que la musique lue ne bouge pas quand une page au-dessus est rendue.
- **Défilement automatique** : la position cible met le système de la mesure courante à la ligne de lecture et avance vers le système suivant au fil des mesures ; un ressort à amortissement critique (solution exacte, indépendante de la fréquence d'images) lisse le mouvement. Saut immédiat pour une reprise (retour de plus de 10 % d'écran) ou une cible lointaine ; le suivi se suspend 1,5 s quand l'utilisateur fait défiler au doigt.
- **Taps** : centre = barres d'outils ; tiers gauche/droit = un écran vers le haut/bas (comme le pédalier, 85 % d'écran). Choix fait pour que les zones de tap gardent le même rôle (« précédent / suivant ») dans les deux modes.

### ADR-020 — Transposition passée à Verovio sous forme d'intervalle ; préférence ♯/♭ — *Acceptée*
- **Contexte** : Verovio accepte pour `transpose` un nombre de demi-tons (`+1`), un intervalle (`m2`, `-A1`, `M9`) ou une tonique (`Db`, `C#`). Vérifié avec Verovio 6.4 dans Node (test `src/core/music/accidentals.test.ts`) : une tonique choisit elle-même le sens (pas de contrôle de l'octave), alors qu'un intervalle fixe à la fois l'orthographe et l'octave.
- **Décision** : quand la tonalité écrite est connue, l'application calcule la tonalité d'arrivée (préférence auto / ♯ / ♭ ; auto = le moins d'altérations, ♭ en cas d'égalité, tonalité écrite gardée pour une transposition d'octaves) puis l'**intervalle** correspondant, qu'elle passe à Verovio. La tonalité affichée dans la fenêtre de transposition est donc exactement celle du rendu. En hauteur réelle, on part de la tonalité sonnante de la première partie. Sans tonalité connue, on garde le nombre de demi-tons.
- La préférence est mémorisée par partition et dans les surcharges de setlist.

### ADR-021 — Setlists : pré-chargement du morceau suivant dans un second worker — *Acceptée*
- Pendant la lecture d'un morceau en mode setlist, le morceau suivant est préparé en arrière-plan : lecture des fichiers, XML affiché, **chargement et mise en page dans un second worker Verovio**, rendu de sa première page. Le viewer suivant reprend ce worker tel quel. Ouverture mesurée en e2e : ≈ 1,5 s sans pré-chargement, ≈ 0,4 s avec.
- Un seul emplacement (le morceau suivant) pour borner la mémoire : au plus deux instances Verovio en même temps. Mémoire réelle à mesurer sur téléphone.
- Autres choix de la visualisation faits pendant la phase 2 : le **mode verrouillé** vaut pour la session (il n'est pas enregistré) ; la **demi-page** coupe entre deux systèmes (jamais à travers une portée) ; l'appui long sur le métronome lance le **métronome seul**.

### ADR-022 — TypeScript 6 épinglé — *Acceptée (à revoir)*

### ADR-023 — Distribution des APK par les Releases GitHub — *Acceptée*

### ADR-024 — « Partager vers » : plugin `@capgo/capacitor-share-target` — *Acceptée*
- **Besoin** : recevoir des partitions partagées depuis une autre application (mail, messagerie, Drive) : intents Android `SEND` (un fichier) et `SEND_MULTIPLE` (plusieurs), qui transmettent les fichiers dans `EXTRA_STREAM` et non dans l'URL de l'intent (que `@capacitor/app` ne lit que pour `VIEW`).
- **Options étudiées** : `send-intent` (Capacitor 7 au mieux, peu suivi) ; un petit plugin Java local dans `android/` ; **`@capgo/capacitor-share-target`** 8.x (licence MPL-2.0, compatible GPL ; Capacitor 8 ; publié le 2026-11-13, maintenu activement).
- **Décision** : `@capgo/capacitor-share-target`. Il gère les deux intents, **copie chaque fichier dans le cache de l'application** (le droit de lecture accordé par l'application d'origine ne dure pas) et donne son nom d'affichage et son type MIME ; ses copies de plus d'un jour sont effacées. **Démarrage à froid** : Capacitor transmet l'intent de lancement aux plugins à la création du pont, et le plugin garde l'événement `shareReceived` jusqu'à ce que l'interface s'y abonne ; **à chaud** (`launchMode singleTask`), il arrive par `onNewIntent`. Pas de code natif à maintenir.
- **Côté application** (`src/core/import/openWith.ts`) : lecture de chaque copie (`file://`), import, suppression de la copie ; un seul fichier → ouverture de la partition (comme « Ouvrir avec… »), plusieurs → bilan d'import. Les filtres d'intents `SEND` / `SEND_MULTIPLE` reprennent les types MIME du filtre `VIEW` (`.mscz` n'a pas de type MIME officiel : `octet-stream` et `zip` sont acceptés, le contenu est vérifié à l'import).
- **À vérifier** : build Gradle par la CI (pas de SDK Android en local) et essai sur téléphone.

### ADR-025 — Cache disque des pages rendues ; ouverture des gros conducteurs — *Acceptée*
- **Constat** (Chromium headless, e2e `performance.mjs`) : ouvrir Toccata (7 parties, 1,6 Mo de MusicXML) prend ≈ 3,6 s, dont ≈ 1,1 s de démarrage de Verovio (compilation du WASM dans le worker), ≈ 0,8 s de chargement et mise en page, ≈ 0,2 s de préparation du XML (4 analyses DOM et 3 sérialisations).
- **Décision 1 — cache disque** (`src/core/render/renderCache.ts`, dossier cache de l'application) : pour un **XML affiché** et un **jeu d'options Verovio** donnés, on garde la mise en page (nombre de pages, identifiants des mesures, page de chaque mesure) et le SVG de chaque page déjà rendue. La **clé** est un SHA-256 du XML affiché (parties, silences regroupés, noms… y sont déjà), de **l'objet d'options Verovio entier** (JSON à clés triées : toute nouvelle option, police musicale comprise, entre automatiquement dans la clé) et des versions de Verovio et de l'application. Taille limitée à 64 Mo, entrées les moins récemment utilisées évincées d'abord ; index JSON écrit en différé (et au passage en arrière-plan). Paramètres → Stockage affiche l'espace utilisé et vide le cache.
- Sur une partition déjà vue avec les mêmes réglages, **Verovio n'est pas chargé** pour afficher : mise en page et pages viennent du disque ; le worker ne charge la partition que pour une page absente du cache ou un élément inconnu. Pour que ces pages se mélangent sans souci avec celles d'un worker neuf, les identifiants Verovio sont rendus **déterministes** (`xmlIdSeed`, sinon ils sont aléatoires à chaque chargement).
- **Décision 2** : le XML affiché est préparé en **une seule analyse DOM et au plus une sérialisation** (filtrage des parties, silences multi-mesures et noms sur le même document ; XML d'origine rendu tel quel s'il n'y a rien à changer).
- **Décision 3** : le worker Verovio est **démarré dès l'ouverture** de la visualisation, en parallèle de la lecture des fichiers et de la préparation du XML.
- **Résultats** (e2e, PC) : préparation du XML ≈ 190 → 70 ms ; première ouverture de Toccata ≈ 3,6 → 2,8 s ; **réouverture ≈ 2,9 → 0,85 s** (medley 5 parties : 3,0 → 2,1 s, puis 2,4 → 0,75 s). Mémoire : les workers de rendu (visualisation, pré-chargement de setlist) et d'import sont bien terminés en quittant la visualisation ou la setlist (vérifié par l'e2e).
- **Pistes suivantes** : compiler le WASM de Verovio une seule fois (aujourd'hui ≈ 1 s par worker) ; mesures sur un téléphone modeste.
- **Complément (2026-11-27, bug « page blanche » sur iPhone, voir TESTS_APPAREIL)** : une page est toujours dessinée **à partir de la mise en page pour laquelle elle a été demandée**. Les opérations du worker passent par une file (une à la fois), chacune ramenant d'abord le worker au XML et aux options de sa demande ; une page est écrite sur disque sous la clé de *cette* mise en page. La visualisation compare la géométrie demandée à la **dernière demandée** (pas à la dernière affichée) : après A → B → A pendant la mise en page de B, A est remise en page. Une page inexistante ou vide (`viewBox="0 0 0 0"`, réponse de Verovio pour une page hors de sa mise en page) est une **erreur**, jamais affichée ni mise en cache ; une page qui échoue ou tarde (30 s) affiche un message et **« Réessayer »** (nouveau worker), jamais une scène vide. Format du cache passé à 2 : les pages mises en cache par la 0.6.0, peut-être fausses, ne sont pas reprises.

### ADR-026 — Lecture audio de la partition : MIDI à l'import, spessasynth + FluidR3Mono, horloge commune, mixeur — *Acceptée (2026-11-26)*, remplace ADR-010 pour l'audio
- **Demande du porteur** : entendre la partition pendant le défilement automatique, avec un **mixeur par partie** (volume, muet, solo) et des raccourcis « tous / moi seul / sans moi » tirés du profil « My instrument ».
- **MIDI à l'import** : webmscore produit en plus un fichier MIDI par partition, `saveMidi(midiExpandRepeats = true, exportRPNs = true)` (reprises dépliées comme la timeline), rangé dans `scores/<id>/score.mid`. `IMPORTER_VERSION` passe à 3 : les partitions existantes sont **réimportées automatiquement** depuis leur fichier d'origine (ADR-018).
  - **Spike S7** (`spikes/s7-midi/`, Node, 4 partitions du corpus, parties masquées rendues visibles comme à l'import) : début de chaque mesure de la timeline (`savePositions(false)`) contre la note MIDI la plus proche : **écart maximal 0,71 ms** (arrondi des positions à la ms), **sans dérive** jusqu'à la fin des partitions (12 min 30 pour la plus longue, 389 mesures jouées). Le temps MIDI et le temps de la timeline sont donc le même temps.
  - **Pistes et canaux** : format 1, **une piste par portée** dans l'ordre de la partition, nommée comme la partie ; les portées d'une partie partagent ses canaux ; **un canal par canal d'instrument MuseScore** (trompette « ouverte » + « sourdine » = 2 canaux) ; batterie sur le **canal 10** (index 9) ; au-delà de 16 canaux, ports MIDI (méta-événement `FF 21`, canal + 16 × port). Les canaux de chaque partie sont calculés à l'import (nombre de portées lu dans le MusicXML) et rangés dans `Part.midiChannels` (`core/audio/partMapping.ts`).
- **Synthétiseur** : **[spessasynth_lib](https://github.com/spessasus/spessasynth_lib)** 4.4 (Apache-2.0, compatible GPL-3 ; maintenu activement, version du 2026-11-20) : SF2/SF3/DLS, AudioWorklet (pris en charge par la WebView Android depuis Chrome 66), événements datés à l'échantillon près (`{ time }`), canaux au-delà de 16, gain par canal, préchargement des échantillons d'un fichier MIDI.
  - **Non retenu** : js-synthesizer / FluidSynth WASM (LGPL, plus lourd, pas de file d'événements datés côté JS), `synthAudio` de webmscore (rendu hors ligne, pas de mixeur en direct ni de changement de tempo instantané), le séquenceur de spessasynth (sa propre horloge démarre « dès réception » : décalage inconnu avec le décompte et le défilement).
- **Banque de sons** : **FluidR3Mono_GM.sf3 2.312** (Frank Wen, version mono de Michael Cowgill), **licence MIT**, **14,6 Mo** (échantillons Ogg Vorbis), telle que livrée par MuseScore 2.3.2 (`https://raw.githubusercontent.com/musescore/MuseScore/v2.3.2/share/sound/FluidR3Mono_GM.sf3`, SHA-256 `cfcd66d8…62794ec2`). Pas dans git (taille) : `scripts/fetch-soundfont.mjs` la télécharge après `npm install` (vérification SHA-256 ; hors ligne : copie manuelle ou `SOUNDFONT_FILE=…`). Licence recopiée dans `public/soundfonts/FluidR3Mono_License.md`. Écartées : FluidR3Mono de MuseScore 3.6 (23,7 Mo), GeneralUser GS (≈ 30 Mo), TimGM6mb (GPL-2 : « or later » non vérifié).
- **Chargement paresseux** : rien n'est chargé tant que le son n'est pas voulu (son activé ou ▶ avec le son activé) ; alors le module spessasynth (≈ 860 ko, 270 ko gzip, chunk séparé), son AudioWorklet (≈ 840 ko) et la banque sont chargés **une fois pour l'application**, puis les échantillons utilisés par la partition sont décodés d'avance (pas de craquement aux premières notes). Mesuré en e2e (PC) : **≈ 1,1 s** de l'activation au son prêt. Le synthétiseur est libéré 60 s après la fermeture de la dernière visualisation (les setlists rouvrent une visualisation par morceau). Mémoire : banque compressée (14,6 Mo) + échantillons décodés plafonnés à 96 Mo (`decodedSampleBudget`, au-delà les moins récents sont redécodés).
- **Changer de banque de sons** : remplacer `SOUND_BANK` dans `src/core/audio/synth.ts` et l'URL/empreinte de `scripts/fetch-soundfont.mjs` par n'importe quel SF2/SF3/DLS General MIDI (ex. MuseScore_General.sf3, ≈ 36 Mo, MIT), mettre sa licence dans `public/soundfonts/` et `src/app/thirdPartyLicenses.ts`. Rien d'autre n'en dépend.
- **Synchronisation** : une seule `AudioContext` pour l'application (`core/audio/audioContext.ts`) ; le `PlaybackEngine` et son ordonnanceur « lookahead » envoient au synthétiseur les événements MIDI des **200 ms suivantes** avec leur **heure exacte** `clock.timeOf(ms)` (même horloge que le métronome et le défilement) : facteur de tempo, reprises (temps MIDI = temps timeline), décompte (le son commence à la première mesure), départ depuis une mesure (« aller à », appui long) avec **rétablissement de l'état des canaux** (programme, volume, panoramique, RPN, pitch bend). Une note en retard de plus de 60 ms (fil principal bloqué) est sautée plutôt que jouée à contretemps. **Pause / saut** : les messages déjà envoyés ne peuvent pas être annulés ; la sortie est coupée en 20 ms (queue de réverbération comprise) et un « all sound off » suit le dernier message envoyé ; la reprise attend ce moment. **Latence** : la position affichée (surlignage, tournage, clignotement du métronome) est décalée de `outputLatency + baseLatency` pour coller à ce qu'on entend.
- **Mixeur** : volume (courbe quadratique, 50 % ≈ −12 dB), muet, solo par partie → gain de chaque canal du synthétiseur ; volume général. Raccourcis « Tous », « Moi seul », « Sans moi » : ils règlent muet/solo à partir des parties qui correspondent au profil « My instrument » (les volumes sont gardés). Mixeur et son activé/coupé **mémorisés par partition** (`ScoreViewState.mixer`, `soundEnabled`) ; en setlist, le mixeur est une **surcharge du morceau**. Paramètres : son activé par défaut, volume par défaut.
- **Interface** : bouton haut-parleur dans la barre du bas ; toucher = feuille « Son » (activer, volume, mixage rapide, parties) qui laisse la partition visible ; appui long = son activé/coupé. - **Taille de l'APK** : **+ ≈ 16,3 Mo** (banque 14,6 Mo, déjà compressée ; AudioWorklet 0,84 Mo ; module 0,86 Mo) : de ≈ 30 Mo à ≈ 46 Mo installés (build web : 43 Mo dans `dist/`).
- **À vérifier sur téléphone** : latence réelle et alignement visuel, craquements (AudioWorklet sur un téléphone modeste, gros conducteurs), mémoire, temps de chargement de la banque, coupure du son en arrière-plan.
- **Complément (2026-11-28) — métronome joué par le synthétiseur, horloge du synthétiseur recalée** :
  - **Retour du porteur** (téléphone Android, son activé) : les clics du métronome et la musique ne sont pas bien synchronisés.
  - **Cause, mesurée** (Chromium headless, sortie enregistrée échantillon par échantillon avec l'heure de l'`AudioContext`) : les clics étaient à l'heure (oscillateurs Web Audio, **+1,6 ms**), mais **chaque note du synthétiseur arrivait ≈ 260 ms en retard**. spessasynth joue un message daté quand **sa propre horloge** atteint l'heure du message ; cette horloge part de l'heure du contexte à la création du processeur, puis n'avance que des échantillons rendus. Chaque fois que le fil audio saute des blocs (banque analysée dans l'AudioWorklet au chargement, échantillons décodés avant la lecture, téléphone chargé), l'horloge du contexte avance et pas celle du synthétiseur : le retard s'accumule (plus grand sur un téléphone, et croissant à chaque craquement). Le surlignage, calé sur l'horloge du contexte, était donc aussi en avance sur le son.
  - **Correction 1, l'horloge** : un petit module d'AudioWorklet chargé avant celui de spessasynth enveloppe `registerProcessor` et, à chaque bloc, remet l'horloge du synthétiseur à l'heure du contexte (+ un demi-bloc : un message tombe sur la limite de bloc la plus proche, ±1,3 ms à 48 kHz, au lieu de jusqu'à un bloc de retard). Il lit un détail interne de spessasynth_lib 4.4 (`core.synthesizer.currentTime`) et ne fait rien s'il change ; `e2e/metronome-sync.mjs` mesure l'alignement, une mise à jour de la bibliothèque qui le casserait serait vue.
  - **Correction 2, le métronome passe par le synthétiseur** (idée du porteur) : **son activé**, les clics sont des **notes MIDI** envoyées par le même ordonnanceur, dans la **même file de messages** et avec **la même heure** `clock.timeOf(ms)` que les notes du même temps : ils démarrent dans le même bloc de rendu, ils ne peuvent plus dériver l'un de l'autre. Choix d'envoyer des événements datés plutôt que d'ajouter une piste au fichier MIDI : le séquenceur de spessasynth n'est pas utilisé (voir plus haut), et les clics suivent déjà la timeline (`core/audio/metronome.ts`, `metronomeNotes`) : changements de métrique, temps à la noire pointée en 6/8, 9/8, 12/8, changements de tempo, reprises dépliées, accent au premier temps, décompte (joué lui aussi par le synthétiseur, avant la musique). Facteur de tempo, départ depuis une mesure (« aller à », appui long), pause et reprise : comme les notes.
  - **Canal et son** : un **canal dédié**, le premier après ceux de la partition et après les 16 du premier port (en pratique 17, index 16 ; jamais le canal 10 de la batterie de la partition), mis en **batterie** (`setDrums`, banque 128), kit Standard, sec (envois de réverbération et chorus à 0). Sons : **Wood Block aigu (76) pour le premier temps, grave (77) pour les autres**, présents dans le kit Standard de FluidR3Mono (vérifié dans la banque) et de toute banque GM ; « Metronome Click / Bell » (33/34) existent aussi dans FluidR3Mono mais sont des ajouts GS, absents de beaucoup de banques GM.
  - **Métronome coupé pendant la lecture** : les messages déjà envoyés ne peuvent pas être retirés de la file du synthétiseur : le canal est rendu muet aussitôt (volume CC 7 à 0), son son coupé après le dernier clic déjà envoyé, puis son volume rétabli (messages datés, dans l'ordre) pour les clics suivants. Son coupé ou activé pendant la lecture : les clics changent de chemin à la position courante, sans clic doublé.
  - **Son coupé** (défilement silencieux, « métronome seul ») : le clic Web Audio (oscillateur) reste. Dans les deux cas, le **point de pulsation** clignote à l'heure du clic, décalée de la latence de sortie (`outputLatency + baseLatency`) : la même pour le synthétiseur et pour l'oscillateur, puisqu'ils sont maintenant sur la même horloge.
  - **Mixeur** : une ligne **« Métronome »** (volume, bouton muet) au début des parties. Son volume vaut par défaut le **volume du métronome des Paramètres** et se règle **par partition** (`MixerState.metronome`, donc aussi par morceau de setlist) ; il s'applique au clic du synthétiseur comme à l'oscillateur. Le bouton muet **arrête le métronome** (le même réglage que le bouton métronome de la barre du bas : un seul interrupteur). **Pas de solo** pour le métronome, et le **solo d'une partie ne le coupe pas** : c'est une aide au travail (« moi seul » + métronome est un usage courant) ; pour ne plus l'entendre, on le coupe. Le volume général du son s'applique au clic du synthétiseur (tout le son passe par lui), pas à l'oscillateur.
  - **Mesuré** (`e2e/metronome-sync.mjs`, Chromium headless, medley pour brass band) : retard des clics joués par le synthétiseur **+3,3 ms** (médiane, décompte compris), retard des notes de batterie **+2,3 ms**, **écart clic / note −1,0 ms** (seuil du test : 5 ms) ; **avant** : clic +1,6 ms, notes ≈ +260 ms, soit un écart d'environ **260 ms** sur PC (plus sur un téléphone). Tests unitaires : `core/audio/metronome.test.ts` (piste du métronome, messages MIDI, clics du `MidiPlayer`, aiguillage synthétiseur / oscillateur du `PlaybackEngine`).
- **Complément (2026-11-28, soir) — canaux par partie, notes sûres, arrêt neutre, levées** (signalement sur Stay With Me, détail dans `docs/TESTS_APPAREIL.md`, analyse `spikes/s8-audio-debug/`) :
  - **Canaux** : au-delà de 16 canaux, webmscore (MuseScore 4.0) écrit le canal **modulo 16** avec le port 0 : des parties partageaient des canaux (programmes écrasés, solo inexact). La correspondance « une piste par portée, un canal par canal d'instrument » reste vraie, mais le fichier est maintenant **réécrit à l'import** (`core/audio/midiChannels.ts`) pour qu'**aucun canal ne soit partagé par deux parties** : le premier propriétaire garde son canal, les autres prennent les premiers canaux libres de leur sorte (mélodique / batterie = canal 10 de chaque port), au-delà de 16 par des méta-événements de port (`FF 21`), que `midiFile.ts` lisait déjà et que spessasynth gère (canaux ajoutés). Le mixeur reste un gain par canal, désormais exact par partie. Écarté : filtrer les notes par piste (les programmes et contrôleurs d'un canal partagé resteraient mélangés). Le type de partie « batterie » vient des métadonnées de webmscore (`hasDrumStaff`), sinon des notes `<unpitched>` du MusicXML.
  - **Notes** : le lecteur MIDI ne trie plus « toutes les note off d'abord » mais **apparie note on / note off dans l'ordre du fichier** (par piste, canal, touche), ignore les notes de durée nulle et les note off orphelines, et fusionne les notes qui se chevauchent sur un canal (rejouée, relâchée une fois) : chaque note on a exactement une note off, jamais deux voix pour une touche d'un canal (spessasynth relâche une voix par note off).
  - **Arrêt** (pause, saut, fin) : en plus de « all notes off » / « all sound off », pédale relâchée, « reset all controllers » (RP-015 dans spessasynth : pitch bend, modulation, expression… ni volume, ni programme, ni le drapeau batterie du métronome) et pitch bend recentré, sur tous les canaux ; l'état de la position de départ est ensuite rétabli comme avant.
  - **Levées et mesures incomplètes** : la timeline enregistre la longueur réelle des mesures incomplètes (`TimelineEvent.fill`, lue dans le MusicXML ; `fromEnd` pour une levée ou la seconde moitié d'une mesure coupée). Le temps du métronome vient du tempo (`beatMs`), une levée compte ses temps depuis sa fin, et le décompte fait N mesures entières sur la même grille **plus les temps manquants de la levée**. `IMPORTER_VERSION` 5.

### ADR-027 — Application web installable (PWA) pour l'iPhone et les navigateurs, sur GitHub Pages — *Acceptée (2026-11-27)*
- **Demande du porteur** : utiliser Pupitre **aussi sur iPhone**, sans App Store (ADR-005), et **hors ligne en répétition**. Réponse : le même code, construit en **application web installable** (PWA), publiée sur **https://artiskongit.github.io/mscz_viewer/** et installée depuis Safari (Partager → « Sur l'écran d'accueil »). Elle marche dans tout navigateur récent (Chrome, Edge, Firefox, Safari).
- **Build séparé** : `npm run build:pwa` (`vite build --mode pwa`) → `dist-pwa/`, avec `base: '/mscz_viewer/'` ; le build Android (`npm run build` → `dist/`, base `/`) et le serveur de dev ne changent pas. Toutes les URL d'exécution suivent `import.meta.env.BASE_URL` (script et fichiers de webmscore, banque de sons, workers et AudioWorklet émis par Vite, favicon). `__PWA__` (défini par Vite) active le service worker et l'interface hors ligne dans ce build seulement. Un plugin Vite (`scripts/pwaPlugin.ts`) écrit le manifeste, `404.html` et `sw.js`.
- **Routage** : `IonReactRouter` avec `basename` tiré de `BASE_URL` (URL propres, identiques à l'application Android). GitHub Pages ne connaît pas les routes de l'application : **`404.html` est une copie de `index.html`** (servie avec le statut 404 pour toute URL inconnue, le routeur lit alors l'URL). Une fois le service worker installé, toute navigation reçoit `index.html` depuis le cache (liens profonds hors ligne). **Non retenu** : un routeur à hachage (`#/viewer/…`) pour le seul build web : URL différentes entre les deux builds, et rien à gagner puisque `404.html` suffit.
- **Hors ligne : tout est mis en cache dès l'installation.** Le service worker (`src/pwa/sw.js`, écrit à la main, sans Workbox) **pré-cache tous les fichiers du build** à son installation : **≈ 44 Mo** (webmscore 17,7 Mo, banque de sons 14,6 Mo, Verovio 8,3 Mo dans le worker de rendu, spessasynth 1,7 Mo, interface ≈ 2 Mo). Après la première ouverture (en ligne), l'import, le rendu et le son marchent **sans réseau**.
  - **Non retenu** : pré-cache de l'interface seule + mise en cache au premier usage, avec une action « Rendre disponible hors ligne ». Le porteur doit pouvoir compter sur l'application en répétition : un fichier jamais utilisé avant (le moteur d'import, la banque de sons) manquerait justement hors ligne. Le coût (44 Mo une fois) est celui de l'APK.
  - **Robustesse** : chaque fichier est rangé sous `<url>?__rev=<empreinte>` ; un téléchargement interrompu **reprend** où il s'était arrêté (les fichiers déjà rangés sont gardés, nouvelle tentative au lancement suivant ou par le bouton de Réglages) ; une **mise à jour** ne télécharge que les fichiers qui ont changé ; chaque fichier est **vérifié par son empreinte SHA-256** (un CDN qui servirait une ancienne copie fait échouer l'installation, qui sera retentée) et téléchargé sans le cache HTTP (GitHub Pages autorise 10 min de cache). Requêtes : cache d'abord pour les fichiers du build, `index.html` pour toute navigation, réseau pour le reste.
  - **Suivi** : Réglages → Stockage → « Utilisation hors ligne » : progression du téléchargement (Mo reçus / total, barre), « Prêt : l'application fonctionne sans réseau (42 Mo sur cet appareil) », ou « Pas encore entièrement téléchargé » avec un bouton « Télécharger pour l'utilisation hors ligne ».
- **Mises à jour** : une nouvelle version déployée est téléchargée en arrière-plan (vérification au lancement et au retour dans l'application, au plus toutes les 30 min) ; elle attend, puis un toast **« Nouvelle version disponible — Recharger »** la fait prendre la main (`skipWaiting`) et recharge la page. Sans action, elle s'applique quand toutes les fenêtres de l'application sont fermées.
- **Stockage persistant** : `navigator.storage.persist()` est demandé au lancement ; l'état est affiché dans Réglages → Stockage (« Stockage protégé »), avec un bouton pour le redemander. Les partitions sont dans IndexedDB (Capacitor Filesystem sur le web), les fichiers de l'application dans le Cache Storage.
- **Manifeste** : nom « Pupitre », `start_url` et `scope` = `/mscz_viewer/`, `display: standalone`, couleurs du logo (`theme_color` `#24398f`, `background_color` `#f4ecd8`), icônes 192, 512 et 512 « maskable » ; pour iOS : `apple-touch-icon` 180 px (opaque), `apple-mobile-web-app-capable`, barre d'état `default` (bande à part, lisible en thème clair et sombre), titre. Icônes générées depuis le logo par `scripts/generate-icons.mjs` (`public/icons/`). `viewport-fit=cover` : les barres d'Ionic évitent l'encoche et l'indicateur d'accueil ; la partition aussi (côtés en paysage, haut et bas quand les barres sont masquées).
- **Particularités de l'iPhone (Safari / WebKit)** :
  - **Import** : iOS grise les fichiers dont il ne connaît pas le type quand `accept` ne liste que des extensions (`.mscz` n'a pas de type déclaré) : **pas de filtre sur iPhone/iPad**, le format est vérifié après le choix (« format non pris en charge »).
  - **Son** : `navigator.audioSession.type = 'playback'` (Safari ≥ 16.4) pour que le son et le métronome ne soient pas coupés par le bouton silencieux ; l'`AudioContext` est créée dans le geste de l'utilisateur et débloquée par un échantillon silencieux.
  - **Écran allumé** : API Screen Wake Lock (iOS ≥ 16.4 dans Safari ; dans l'application installée depuis iOS 18.4) ; le réglage est masqué si l'API manque.
  - **Indisponible dans le build web** (masqué ou sans effet) : **« Ouvrir avec » et « Partager vers »** (une PWA ne peut pas recevoir de fichiers sur iOS), **verrouillage de l'orientation** (réglage masqué hors Android).
- **Limites sur iOS** :
  - **Stockage** : l'application installée a son **propre stockage, séparé de Safari** : il faut l'ouvrir une fois en ligne depuis l'écran d'accueil pour le téléchargement hors ligne, et les partitions importées dans Safari n'y sont pas. Safari peut **effacer les données d'un site non utilisé depuis 7 jours** ; une application installée sur l'écran d'accueil n'y est pas soumise (à confirmer sur l'appareil), et le stockage persistant est demandé. Quota largement suffisant (≈ 60 % du disque depuis iOS 17).
  - **Mémoire** : WebKit tue les pages gourmandes plus tôt que la WebView Android ; webmscore (import) et Verovio tournent dans des workers séparés, libérés après usage. Gros conducteurs à tester sur un iPhone ancien.
  - **Arrière-plan** : iOS suspend l'application web quand elle n'est plus à l'écran (le son s'arrête).
- **Déploiement** : `.github/workflows/pages.yml` construit `dist-pwa` et le publie sur GitHub Pages (`actions/upload-pages-artifact` + `actions/deploy-pages`) à **chaque tag `v*`** (comme l'APK) et à la demande. Prérequis : Pages activé avec la source « GitHub Actions » (Settings → Pages). La CI construit aussi la PWA.
- **Tests** : `e2e/pwa.mjs` construit la PWA, la sert comme GitHub Pages sous `/mscz_viewer/` (URL inconnues → `404.html`), vérifie le manifeste, le lien profond, l'enregistrement du service worker et le téléchargement complet, puis **arrête le serveur et coupe le réseau** : rechargement, liens profonds, import, rendu et **son** (niveau mesuré) ; enfin une nouvelle version déployée fait apparaître « Nouvelle version disponible — Recharger ». Dans **Chromium (Pixel 7)** et dans **WebKit (profil iPhone 14)** de Playwright (`npx playwright install webkit` ; sur une distribution non prise en charge, les bibliothèques manquantes `libavif16`, `libgav1-1`, `libyuv0` peuvent être extraites des paquets dans `~/.cache/ms-playwright/webkit-*/minibrowser-wpe/lib/`). WebKit de Playwright n'est pas Safari iOS : l'appareil reste à tester (`docs/TESTS_APPAREIL.md`).

### ADR-028 — Changement de clé par instrument, dans le XML affiché — *Acceptée (2026-11-27)*
- **Demande du porteur** : changer la clé d'un instrument, surtout entre clé de sol et clé de fa (trombone, euphonium, tuba qui lisent l'autre clé).
- **Où** : dans la préparation du XML affiché (`src/core/musicxml/clefs.ts`, fonction pure testée), pas dans Verovio (aucune option de clé). On réécrit les `<clef>` ; les **hauteurs ne changent pas** (mêmes notes écrites, replacées par Verovio). La transposition (`transpose` de Verovio), la hauteur réelle et le filtrage des parties restent indépendants. Le choix fait partie de la clé de contenu (rechargement Verovio) ; le **cache de rendu** est juste par construction, sa clé hachant le XML affiché.
- **Choix proposés** : Originale, sol, **sol 8 en bas** (`clef-octave-change` −1 : un trombone y est lu à sa tessiture, sans lignes supplémentaires — ce que fait MuseScore pour le ténor), fa, ut 3e et ut 4e ligne. **Non retenu** : fa 8va / 8vb (rares) ; une clé « Si♭ clé de sol » mêlant clé et transposition.
- **Portée de l'option** : un choix **par partie**, appliqué à **toutes ses portées à hauteurs** (piano : les deux portées dans la clé choisie). Plus simple qu'un choix par portée, et le besoin vise les instruments à une portée. Les portées de percussion, de tablature ou sans hauteur ne sont jamais touchées (pas de menu si la partie n'a pas de portée à hauteurs).
- **Changements de clé en cours de morceau** : retirés (la clé choisie vaut pour tout le morceau). Les remplacer un à un par la même clé afficherait des clés de rappel inutiles et couperait les silences multi-mesures.
- **Préréglage brass band « Si♭ clé de sol »** (fenêtre Transposition) : +2 demi-tons +1 octave (neuvième majeure) et passage en clé de sol des parties affichées en clé de fa, ut 4e ou sol 8vb. La transposition reste globale (comme le reste de l'application) : le préréglage vise une partie affichée seule. **Non retenu** : basses en Mi♭ / Si♭ (tuba de brass band, +21 / +26) : à ajouter si demandé.
- **Stockage** : `clefOverrides?: Record<musicXmlId, ClefChoice>` dans `ScoreViewState` (absent = clés de la partition, pas de migration) et dans la surcharge d'entrée de setlist (une table vide y signifie « clés de la partition » quand la partition a ses propres choix).

### ADR-029 — Dossiers dans la bibliothèque — *Acceptée (2026-11-28)*
- **Demande du porteur** : ranger les partitions dans des dossiers.
- **Modèle** : `Folder { id, name, parentId?, createdAt }` (dossiers **imbricables**) dans l'index `library.json` (et non un fichier à part : une seule écriture atomique pour « supprimer un dossier et remonter son contenu ») ; `Score.folderId?` (absent = racine). `schemaVersion` 1 → 2, migration sans perte (partitions à la racine). Une partition est dans **un seul** dossier (pas d'étiquettes multiples : ce sera le rôle des tags, phase 4).
- **Suppression** d'un dossier : jamais de partition supprimée ; son contenu (partitions et sous-dossiers) remonte au parent. **Déplacement** d'un dossier : refusé dans lui-même ou un sous-dossier (contrôle dans le dépôt + entrées grisées dans le choix).
- **Navigation** : une route par dossier, `/library/folder/:folderId`, rendue par le même `LibraryScreen` ; chaque niveau est une page de la pile Ionic, donc la flèche de l'en-tête et le **bouton retour d'Android** remontent d'un niveau sans code spécifique (le `defaultHref` de la flèche pointe vers le dossier parent pour un lien direct). **Non retenu** : un paramètre `?folder=` sur `/library` (une seule page Ionic pour tous les niveaux : retour matériel et animations à gérer à la main).
- **Bouton « + »** : `IonFab` + `IonFabList` vers le haut (Importer, Nouveau dossier), boutons agrandis à 48 px. **Non retenu** : une feuille d'actions (une étape de lecture de plus, les icônes demandées disparaissent).
- **Imports sans bouton** (« Ouvrir avec… », « Partager vers… », sélection rendue après un redémarrage d'Android) : gérés **une seule fois** pour toute l'application (`ExternalImports`, plus dans l'écran — plusieurs pages de bibliothèque peuvent être empilées), vers le dossier dont l'URL est affichée (`/library/folder/<id>`), sinon la racine. Les fenêtres de progression d'import sont, de même, uniques (`LibraryProgress`).
- **Sélection multiple** : appui long (0,5 s, annulé si le doigt bouge) ou « Sélectionner » dans le menu ⋮ ; seule action groupée : **Déplacer**. Le retour Android quitte la sélection (priorité 150 sur `ionBackButton`).
- **Recherche** : toute la bibliothèque, chemin affiché sous chaque résultat. Le tri s'applique dans le dossier ; les dossiers sont triés par nom.
- **Tests** : `libraryRepository.test.ts` (migration, réparation, création, renommage, déplacements, cycles, suppression), `importScore.test.ts` (import dans un dossier), e2e `folders.mjs` (en et fr).
